# 跨客户端模型“降智”检测通用技术方案

**版本：v1.1**

**更新日期：2026-10-17**

**适用范围：** OpenAI Codex、第三方 AI CLI、IDE Agent、API 中转网关、自研 LLM 客户端及其他支持兼容协议的工具。

**方案定位：** 基于协议能力、服务端遥测、推理预算与行为基线的多维度模型能力检测系统。

---

## 一、背景与目标

### 1.1 背景

在使用 Codex、第三方 AI 客户端及 API 中转服务时，用户可能观察到以下现象：

1. 选择高能力模型，但实际响应质量明显下降。
2. 请求模型名称与服务端返回的模型名称不一致。
3. 模型名称保持一致，但底层执行引擎遥测信息出现异常。
4. 推理 Token 数量在特定位置异常集中。
5. 高推理档位未按预期生效。
6. WebSocket、模型控制流等高级功能不可用。
7. 复杂编程任务的正确率、连续性与工具使用能力下降。
8. 服务端频繁返回模型容量不足、限流或连接异常。

这些现象可能由多种不同原因造成：

- 服务端模型路由或回退
- 模型或推理配置错误
- API 网关兼容性问题
- 特定执行模式不支持某些功能
- 推理预算或输出预算限制
- 服务端容量与资源调度问题
- 客户端自身的上下文管理与状态机问题
- 模型实际表现变化
- 网络异常、认证失败或请求超时

因此，不能通过单一 Prompt、一次测试结果或某个特定 Header 直接断言模型发生了“降智”。

### 1.2 核心目标

设计一个可移植的独立检测器，尽量不依赖目标客户端的业务逻辑，直接验证模型服务的真实能力及执行环境。

检测器应具备以下能力：

1. 解析目标客户端使用的模型、认证、Provider 和 Endpoint。
2. 使用独立连接执行原生协议探测。
3. 验证 Responses API Mid-turn Steering 功能。
4. 对比请求模型与服务端报告的模型。
5. 收集可用的底层执行引擎遥测信息。
6. 检测推理 Token 分布异常。
7. 通过多次行为测试分析模型指纹变化。
8. 通过标准化任务比较模型能力是否回退。
9. 输出结构化、可追溯的诊断报告。
10. 明确区分已确认异常、疑似异常与无法判定。

### 1.3 核心设计原则

**原则一：独立探测**

检测器必须使用独立的网络连接和响应状态管理，不依赖目标客户端自身的任务队列、正常 Agent 执行状态机或响应流锁。

**原则二：运行路径一致**

探测器应尽可能使用与目标客户端一致的 Provider、Endpoint、模型、推理档位和网络代理配置。

如果无法保证一致性，必须在检测报告中记录差异。

**原则三：认证安全**

只能使用用户合法授权的认证能力。不向未经授权的端点发送 Token，不记录 Token 明文，也不绕过客户端或服务商的访问限制。

**原则四：证据优先**

优先使用服务端实际返回的协议事件、响应模型、错误码和可用遥测信息。

**原则五：多信号交叉验证**

单个异常只能形成对应维度的诊断结果，不得直接推导整体模型性能下降。

**原则六：可移植性**

核心检测器保持客户端无关。不同客户端只需实现统一适配接口。

## 三、客户端认证与连接适配

### 3.1 客户端适配接口

各客户端应实现统一接口，向检测器提供以下信息：

```text
ClientAdapter
  |
  +-- get_client_info()
  |
  +-- get_auth_provider()
  |
  +-- get_provider_config()
  |
  +-- get_model_config()
  |
  +-- get_endpoint()
  |
  +-- get_network_config()
  |
  +-- get_supported_protocols()
  |
  +-- create_authenticated_connection()
```

其中：

- `get_auth_provider()`：返回受控的认证提供器，不直接向报告暴露 Token。
- `get_endpoint()`：返回客户端实际使用的目标地址。
- `get_model_config()`：包含模型名称与推理相关设置。
- `get_network_config()`：包含代理、TLS 和必要的网络设置。
- `create_authenticated_connection()`：由适配层负责合法鉴权并建立独立连接。

### 3.2 OpenAI Codex 适配

参考源码：

https://github.com/openai/codex

建议重点检查：

```text
codex-rs/
  |
  +-- login/
  |     |
  |     +-- src/auth/manager.rs
  |
  +-- codex-api/
  |     |
  |     +-- src/common.rs
  |     |
  |     +-- src/endpoint/responses_websocket.rs
  |
  +-- model-provider-info/
  |     |
  |     +-- src/lib.rs
  |
  +-- core/
        |
        +-- src/client.rs
```

以上路径为源码适配入口，实际修改前应以目标版本或固定提交为准。

Codex 的典型请求端点包括：

| 认证模式 | 典型地址 |
|---|---|
| ChatGPT 登录 | `wss://chatgpt.com/backend-api/codex/responses` |
| OpenAI API Key | `wss://api.openai.com/v1/responses` |
| 自定义 Provider | 根据配置解析 |

以上地址不能硬编码为所有客户端的默认值。

**特别注意：Codex 的 ChatGPT 登录认证与标准 OpenAI API Key 并不等价。**

必须确认认证作用域、授权端点和客户端配置是否允许独立探测，不能假设缓存的任意访问凭证都可用于所有 API。

### 3.3 其他客户端适配

| 客户端类型 | 适配策略 |
|---|---|
| Codex CLI | 复用认证管理及 Provider 配置，另建连接 |
| OpenAI SDK 客户端 | 使用受支持的 Responses WebSocket API |
| Claude Code | 根据实际 Provider 及协议选择检测器 |
| IDE Agent | 通过公开配置或授权接口获取连接能力 |
| API 中转网关 | 复用合法配置的网关地址及认证 |
| 自研工具 | 直接实现统一 Adapter |

对于不使用 OpenAI Responses WebSocket 协议的客户端，Steering 检测应返回：

`NOT_APPLICABLE`

而不能将协议不适用解释为模型被降级。

### 3.4 路径一致性验证

检测器应记录：

```text
client_name
client_version
provider
auth_type
endpoint
requested_model
reasoning_effort
proxy_enabled
protocol
transport
```

进行对照时，还应检查：

- 客户端请求与探测请求是否采用同一后端。
- 是否存在 HTTP 与 WebSocket 的传输差异。
- 是否使用了相同的模型及 reasoning 配置。
- 是否存在额外的网关参数改写。
- 是否启用了不同的工具、上下文或系统指令。

如果差异无法消除，检测结果必须标记为：

`PATH_MISMATCH` 或 `PATH_UNVERIFIED`

## 四、L1：Mid-turn Steering 协议检测

### 4.1 检测目标

验证当前模型与执行模式是否支持 OpenAI Responses API 的原生 Mid-turn Steering 功能。

该功能通过 WebSocket 连接向正在执行的响应追加新的用户输入。

截至本方案更新日期，官方文档明确：

- GPT-6 模型家族支持 Steering。
- GPT-5.6 及更早模型不支持 Steering。
- 该功能仅适用于受支持的模型及执行模式。
- 绑定 conversation 或启用自动 compaction 等不兼容的执行模式不能用于有效的 Steering 能力测试。

Steering 成功仅证明当前执行路径具备特定协议能力，不等于证明模型整体推理能力正常。

### 4.2 初始化条件

检测前应固定以下条件：

```text
protocol = responses_websocket
model = 明确支持Steering的目标模型
conversation = 未绑定
auto_compaction = disabled
agent_mode = single_agent
tools = []
store = false
```

避免同时进行工具调用、自动压缩、多 Agent 调度等操作，以减少无关因素。

### 4.3 建立独立 WebSocket

使用 Adapter 返回的合法连接信息建立 WebSocket。

连接建立之后：

1. 确认认证通过。
2. 确认目标 Endpoint 有效。
3. 确认 WebSocket 协议握手成功。
4. 初始化独立的事件监听循环。
5. 记录连接标识和开始时间。

连接和认证失败时不应继续判定模型能力。

### 4.4 发送初始请求

参考请求：

```json
{
  "type": "response.create",
  "model": "gpt-6-astra",
  "input": "请制定一个软件发布检查计划，列出八个方面，并逐项解释。",
  "reasoning": {
    "effort": "medium"
  },
  "tools": [],
  "store": false,
  "max_output_tokens": 512
}
```

说明：

- 模型名称应由 Adapter 提供。
- 以上 `gpt-6-astra` 仅为示例。
- 必须使用目标 Endpoint 支持的字段。
- Prompt 不应过短，以免响应在 Steering 前已经结束。
- 也不应过长，以免增加探测成本。

### 4.5 捕获初始响应

监听：

```text
response.created
```

提取：

```text
initial_response_id
initial_response_model
created_timestamp
```

其中 `initial_response_id` 为后续 Steering 的目标响应标识。

### 4.6 发送 Steering 请求

收到初始 `response.created` 后，立即在同一连接上发送：

```json
{
  "type": "response.steer",
  "previous_response_id": "<initial_response_id>",
  "input": "请调整为三个最重要的检查项，每项只给出一个核心理由。"
}
```

注意：

1. 必须使用同一条 WebSocket 连接。
2. 不得使用客户端正常对话队列代替原生请求。
3. `previous_response_id` 必须来自当前连接。
4. 不得重复提交已经 accepted 的 Steering。
5. `response.steer` 只携带协议规定的字段。

### 4.7 响应事件监听

检测器应跟踪以下事件：

```text
response.created
response.steer.accepted
response.steer.pending
response.steer.failed
response.incomplete
response.completed
response.failed
error
```

典型成功流程：

```text
WebSocket Connected
        |
        v
response.create
        |
        v
response.created
        |
        v
response.steer
        |
        v
response.steer.accepted
        |
        v
Original Response Terminal Event
        |
        v
Successor response.created
        |
        v
STEERING_SUPPORTED
```

`response.steer.accepted` 仅表示服务端已接收并排队 Steering 输入。

只有在确认后继响应创建时，才应认定 Steering 已提交。

后继响应还应尽可能通过协议提供的关联字段、响应链及事件顺序验证其确实对应本次 Steering。

### 4.8 状态判定

| 事件或错误 | 状态 | 说明 |
|---|---|---|
| accepted + 关联后继 created | `SUPPORTED` | 已确认 Steering 提交 |
| 仅 accepted | `PENDING` | 已接收但未确认提交 |
| steer.pending | `WAITING_INPUT` | 等待工具结果或审批 |
| steering_not_supported | `UNSUPPORTED` | 当前模型或请求模式不支持 |
| invalid_input | `INVALID_PROBE` | 请求不合法 |
| response_not_found | `INVALID_CONTEXT` | 响应关联失败 |
| too_many_pending_steers | `SATURATED` | 待处理输入过多 |
| 响应结束过快 | `RACE_CONDITION` | 未形成有效探测窗口 |
| 认证失败 | `AUTH_ERROR` | 无法验证 |
| 连接中断 | `CONNECTION_ERROR` | 无法验证 |
| 等待超时 | `TIMEOUT` | 无法确认最终状态 |
| 服务端执行失败 | `BACKEND_ERROR` | 后端异常 |

应保留原始 `error.code`，避免把未列出的错误全部归入固定类型。

### 4.9 重要判定边界

以下推论均不成立：

```text
Steering Supported
    != Model Intelligence Normal

Steering Unsupported
    != Model Downgraded

Steering Timeout
    != Model Downgraded

WebSocket Disconnect
    != Model Downgraded
```

对于明确不支持 Steering 的模型，应输出：

`EXPECTED_UNSUPPORTED`

对于理论上支持，但实际返回不支持的模型，应输出：

`UNEXPECTED_UNSUPPORTED`

后一种状态仍需检查请求模式、端点兼容性和认证限制。

## 五、L2：模型路由与实际执行环境检测

### 5.1 检测目标

检测以下信息是否一致：

1. 客户端请求的模型。
2. 初始响应报告的模型。
3. 最终响应报告的模型。
4. 可用遥测中的执行引擎标识。

### 5.2 核心采集字段

```text
requested_model
response_created_model
response_completed_model
telemetry_engine_ids
server_request_id
response_id
client_version
endpoint
transport
timestamp
```

### 5.3 服务端模型名称检查

需要分别记录：

```text
response.created.response.model

response.completed.response.model
```

如果：

```text
requested_model = gpt-6-astra

response_created_model = gpt-5.6-luna
```

则标记：

`MODEL_MISMATCH`

这表示客户端请求模型与服务端报告的响应模型存在明确不一致。

它是较强的路由异常证据，但不能仅凭该字段查明服务端内部为什么发生变化。

### 5.4 执行引擎遥测检查

Linux.do 社区曾报告以下案例：

```text
requested_model:
    gpt-5.6-sol

response_completed_model:
    gpt-5.6-sol

timing_metrics.engine_ids:
    gpt56lun-codex-...
```

该案例表明，公开响应模型名称与底层遥测可能存在差异。

建议尝试收集：

```text
responsesapi.websocket_timing

timing_metrics.engine_ids
```

但必须注意：

- `engine_ids` 不是公开承诺稳定的模型身份字段。
- 其出现与否取决于客户端、服务端和诊断能力。
- 字段命名与内部含义可能随版本变化。
- 不得直接依据固定字符串前缀做永久性判断。
- 应同时保存客户端版本、遥测字段路径及解析器版本。

### 5.5 路由状态分类

| 条件 | 判定 |
|---|---|
| 请求与响应模型一致 | `MODEL_MATCHED` |
| 请求与响应模型不同 | `MODEL_MISMATCH` |
| 模型一致但遥测指向其他家族 | `ROUTING_SUSPECTED` |
| 遥测包含多个引擎 | `MIXED_ENGINE_TELEMETRY` |
| 无法取得模型或遥测信息 | `INCONCLUSIVE` |

对于 `MIXED_ENGINE_TELEMETRY`，不能直接推断最终回答由哪一个模型生成。

### 5.6 Safety Buffering Header 的处理

可能观察到：

```text
x-codex-safety-buffering-enabled

x-codex-safety-buffering-faster-model
```

例如：

```text
requested_model = gpt-6-astra

x-codex-safety-buffering-faster-model = gpt-6-luna
```

这不能证明最终生成答案的模型就是 Luna。

因此：

```text
Safety Buffering Header
    != Model Substitution Proof
```

建议只将这类 Header 保存为辅助元数据，不直接参与确定性的模型替换判定。

## 六、L3：推理预算与异常截断检测

### 6.1 检测目标

检测模型在复杂任务中的推理预算使用情况是否出现异常分布。

Linux.do 社区分析发现，部分 GPT-6 Astra 历史请求的推理 Token 计数集中在：

```text
516
1034
1552
...
```

这些数值符合以下形式：

```text
reasoning_tokens = 518 * k - 2
```

但这只是社区观察到的统计现象，不是公开确认的服务端截断机制。

### 6.2 数据采集

对每次独立请求采集：

```text
model
reasoning_effort
input_tokens
output_tokens
reasoning_tokens
finish_status
incomplete_reason
max_output_tokens
task_category
task_result
request_timestamp
```

如服务端没有提供 `reasoning_tokens`，应将该维度标记为：

`METRIC_UNAVAILABLE`

不能使用模型自行报告的“内部推理长度”替代实际用量统计。

### 6.3 异常候选值

建议建立候选集合：

```text
516
1034
1552
2070
...
```

对应判断：

```python
def is_spike_candidate(tokens: int) -> bool:
    return tokens >= 516 and (tokens + 2) % 518 == 0
```

注意：这是分布探针，不是确定性的截断检测器。

### 6.4 分布分析

建议计算：

```text
total_requests

valid_requests

long_reasoning_requests

spike_candidate_requests

spike_rate

median_reasoning_tokens

p90_reasoning_tokens

p99_reasoning_tokens

completion_rate

task_success_rate
```

其中：

```text
spike_rate =
    spike_candidate_requests
    / eligible_reasoning_requests
```

`eligible_reasoning_requests` 必须使用预先固定的筛选规则。

例如，可以针对 Token 数不低于 516 的正常完成请求单独计算，但必须注明这一筛选会改变统计总体。

不能在观察结果后任意修改分母，以制造异常显著性。

### 6.5 基线对照

推荐比较：

```text
同模型
同Reasoning Effort
同任务类型
同Endpoint
同请求参数
同客户端/协议版本
相近时间窗口
```

如需跨模型比较，必须单独说明模型结构与推理策略差异可能造成 Token 分布不同。

### 6.6 判定逻辑

```text
发现候选集中
       |
       v
检查请求是否正常完成
       |
       v
检查是否受输出Token上限影响
       |
       v
检查任务类型与推理档位
       |
       v
与历史或参考环境比较
       |
       v
检验异常集中是否显著
       |
       v
结合任务正确率判断
```

推荐状态：

| 条件 | 状态 |
|---|---|
| 无可用 reasoning 数据 | `METRIC_UNAVAILABLE` |
| 样本量不足 | `INSUFFICIENT_SAMPLES` |
| 分布与参考基线接近 | `BASELINE_MATCH` |
| 候选位置异常集中 | `REASONING_ANOMALY` |
| 异常集中同时伴随质量下降 | `REGRESSION_SUSPECTED` |

### 6.7 禁止的错误判断

不能使用：

```text
reasoning_tokens == 516
    => MODEL_DOWNGRADED
```

也不能使用：

```text
reasoning_tokens < expected
    => MODEL_DOWNGRADED
```

推理 Token 数受任务难度、提示词、模型策略、执行模式和请求限制共同影响。

**低 Token 数不等于低智能，高 Token 数也不等于高智能。**

## 七、L4：模型行为指纹检测

### 7.1 检测目标

通过固定输入下的输出分布，判断目标模型的行为是否偏离已知参考模型。

### 7.2 实施方式

准备一组经过校准的短任务：

```text
Probe A: 固定格式输出
Probe B: 简单词语选择
Probe C: 常识类别选择
Probe D: 简单多步推理
Probe E: 可自动判分的编程问题
```

每组任务独立执行多次，记录输出结果分布。

### 7.3 参考模型指纹

针对每个参考模型建立：

```text
model_name
model_version
reasoning_effort
probe_id
output_distribution
sample_count
baseline_timestamp
```

比较目标模型和参考模型的分布相似度。

可选方法包括：

- Jensen-Shannon Divergence
- KL Divergence（在分布平滑后使用）
- Bootstrap Confidence Interval
- Likelihood Ratio
- 多类别分类器

具体阈值必须通过独立的参考样本校准。

### 7.4 避免指纹误判

必须考虑：

1. 同一个模型在不同时期可能更新。
2. 多个模型可能产生高度相似的输出分布。
3. 简单题目可能无法区分模型。
4. 推理档位会影响结果。
5. 采样参数会影响结果。
6. 候选模型集合可能不完整。
7. 提示词和客户端系统指令可能影响结果。

应提供：

`UNKNOWN_MODEL`

以及：

`LOW_CONFIDENCE`

不能在候选模型集合不完整时，强制将目标归类为某个已知模型。

### 7.5 不采用自报内部参数作为确定证据

不推荐单独使用以下类型的问题：

```text
What model are you?

What is your internal reasoning budget?

What is your juice number?
```

模型生成的回答不属于可信服务端遥测。

这类提示词最多可以作为经过验证的行为特征之一。

## 八、L5：实际任务能力回归检测

### 8.1 检测目标

最终需要回答的问题是：

**在可比较的条件下，目标模型的实际任务表现是否显著下降？**

### 8.2 推荐任务类型

针对编程 Agent，建议选择：

| 任务类型 | 评价指标 |
|---|---|
| 代码理解 | 关键问题识别正确率 |
| Bug 修复 | 自动化测试通过率 |
| SQL 生成 | 查询正确率 |
| 代码重构 | 行为等价性 |
| 多文件修改 | 功能完成率 |
| 算法问题 | 标准测试正确率 |
| 长上下文任务 | 关键事实保持率 |

### 8.3 测试环境

每次测试应尽量使用：

```text
固定代码仓库快照
固定输入任务
固定系统指令
固定可用工具
固定模型与推理档位
固定资源限制
独立执行环境
```

对于 Agent 任务，还应保留：

```text
tool_call_count
tool_error_count
task_duration
input_tokens
output_tokens
reasoning_tokens
final_test_result
```

### 8.4 统计方法

推荐使用配对测试：

```text
Reference Model / Environment
            |
            +-- Task 1
            +-- Task 2
            +-- Task 3
            +-- ...
            |
            v
       Baseline Results

Target Model / Environment
            |
            +-- Same Task 1
            +-- Same Task 2
            +-- Same Task 3
            +-- ...
            |
            v
        Target Results
```

比较：

```text
task_success_rate
pass_rate_difference
paired_task_delta
confidence_interval
failure_category_distribution
```

建议从 30 次以上的独立样本开始评估，正式样本量由预期检测的效应大小和所需统计功效确定。

不能将 30 次视为任何场景下都充分的证明。

### 8.5 判定

| 条件 | 状态 |
|---|---|
| 无可比较基线 | `BASELINE_REQUIRED` |
| 样本不足 | `INSUFFICIENT_SAMPLES` |
| 差异未达到预设显著性条件 | `NO_CONFIRMED_REGRESSION` |
| 显著低于基线 | `PERFORMANCE_REGRESSION` |
| 存在多个无法控制的环境差异 | `INCONCLUSIVE` |

## 九、综合判定与证据等级

### 9.1 证据强度分级

| 等级 | 证据 | 解释 |
|---|---|---|
| A | 请求模型与服务端响应模型不一致 | 直接的响应模型不一致证据 |
| B | 可信路由遥测指向不同引擎 | 较强辅助证据，语义仍需核实 |
| B | 标准任务出现可重复且显著的质量回退 | 直接的性能回退证据 |
| C | Steering 异常不支持 | 协议或配置能力异常 |
| C | 推理 Token 分布异常 | 推理过程异常线索 |
| D | 模型行为指纹漂移 | 概率性辅助证据 |
| E | Safety Buffering Header | 弱辅助信息 |
| E | 模型自报身份、单次问答失败 | 不足以用于确定判断 |

等级用于描述证据性质，而不是已经校准的统计置信度。

### 9.2 综合状态

建议总体结果采用：

```text
NORMAL
MODEL_MISMATCH
ROUTING_SUSPECTED
PROTOCOL_ANOMALY
REASONING_ANOMALY
PERFORMANCE_REGRESSION
REGRESSION_SUSPECTED
CONFIGURATION_ERROR
INCONCLUSIVE
NOT_APPLICABLE
```

其中：

- `NORMAL`：本次检测范围内没有发现异常，不表示完整证明模型未降级。
- `MODEL_MISMATCH`：服务端报告的模型与请求不一致。
- `ROUTING_SUSPECTED`：遥测存在需要进一步核实的路由差异。
- `PROTOCOL_ANOMALY`：协议功能与明确的预期不一致。
- `REASONING_ANOMALY`：推理用量分布显著偏离参考基线。
- `PERFORMANCE_REGRESSION`：实际任务能力出现可重复的统计回退。
- `REGRESSION_SUSPECTED`：存在多项线索，但尚不足以确定。
- `CONFIGURATION_ERROR`：异常可归因于已确认的配置或参数问题。
- `INCONCLUSIVE`：证据不足或测试失败。
- `NOT_APPLICABLE`：协议或检测方法不适用。

### 9.3 优先级规则

判定时应优先分析：

```text
认证与网络是否有效
        |
        v
请求配置是否正确
        |
        v
实际Endpoint是否一致
        |
        v
服务端响应模型是否一致
        |
        v
底层路由遥测
        |
        v
协议功能支持情况
        |
        v
推理用量异常
        |
        v
行为指纹变化
        |
        v
实际任务回归
```

如果已经发现明确的配置错误，应优先报告并修复配置，再重新执行其他测试。

总体状态可以给出最高优先级异常，但必须保留所有子维度状态，不能覆盖其他异常证据。

## 十一、检测执行策略

### 11.1 快速模式

适合日常手动检查。

执行：

```text
1. 配置检查
2. Steering 探测
3. 响应模型检查
4. 可用遥测检查
```

推荐每个独立协议场景尝试 3 次，以区分稳定结果和偶发竞态。

注意：重试用于排除瞬时失败，不用于将不支持的模型强行测试为支持。

### 11.2 标准模式

适合发现可疑行为后进一步诊断。

执行：

```text
1. 快速模式
2. 推理Token统计
3. 基础行为指纹
4. 少量固定任务测试
```

根据检测成本和任务区分度确定样本数。

### 11.3 深度模式

适合需要严谨证据的情况。

执行：

```text
1. 标准模式
2. 多时间窗口采样
3. 多任务类别对照
4. 可信参考环境对照
5. 置信区间计算
6. 多维度证据交叉验证
```

### 11.4 避免污染正常客户端

要求：

- 不修改已有对话。
- 不取消正在执行的业务请求。
- 不占用正常业务 WebSocket 连接。
- 不向现有 Agent 会话注入探测输入。
- 不修改客户端的默认模型配置。
- 不影响工具调用、审批与任务调度。
- 设置请求次数及 Token 消耗上限。

## 十四、关键限制与误判防护

必须明确以下限制：

**1. Steering 不代表完整模型身份。**

某个模型支持 Steering，并不代表它具有预期的推理能力。

**2. Steering 不支持不代表模型被降级。**

必须考虑模型版本、协议、执行模式及请求配置。

**3. 响应模型名称不是完整的服务端执行证明。**

它可以揭示明确的名称不一致，但不能单独解释所有内部路由行为。

**4. Engine IDs 属于辅助诊断字段。**

不能假设字段永久存在或语义永久稳定。

**5. Safety Buffering Header 不是模型替换证明。**

不能根据备用模型名称直接断言最终回答由该模型生成。

**6. 推理 Token 集中不是截断的充分证据。**

必须结合正常完成状态、Token 限额、任务难度和参考基线。

**7. 行为指纹是概率性的。**

无法保证所有模型都可区分，也不能保证指纹永不漂移。

**8. 少量 Prompt 测试不能证明性能回退。**

必须控制测试条件并使用足够样本。

**9. 独立探测不一定完全复制真实客户端执行环境。**

必须记录系统指令、工具、传输方式及其他潜在差异。

**10. 无法判定是合法且必要的结果。**

不能为了输出结论而将网络错误、缺少遥测或统计不足强行归类为降智。

## 十六、最终结论

本方案不将“降智”定义为某个简单的布尔值，而是拆解为五类独立的检测能力：

| 维度 | 核心问题 |
|---|---|
| L1 协议检测 | 当前服务是否支持预期的高级控制流功能？ |
| L2 路由检测 | 服务端报告的模型及执行遥测是否符合请求预期？ |
| L3 推理检测 | 推理用量及完成状态是否存在统计异常？ |
| L4 指纹检测 | 模型行为分布是否偏离参考模型？ |
| L5 性能检测 | 实际任务能力是否出现可复现的回退？ |

最终判定遵循以下原则：

**协议结果用于判断功能支持，遥测用于识别执行路径线索，统计用于识别异常分布，基准任务用于评价实际能力。**

它们之间相互补充，但不能任意互相替代。

对于需要跨客户端移植的实现，应优先完成认证与 Provider 适配、独立 WebSocket、原生 Steering 探测、响应模型采集和统一 JSON 报告。

在此基础上逐步增加推理预算分析、模型指纹及任务回归评估。

**最终目标不是声称能够 100% 判断模型是否“降智”，而是形成一套可复现、可追溯、可扩展、能够明确区分证据等级的跨客户端模型能力检测体系。**
